# 并行上下文管理设计

## 目标

- 第一步、第二步、第三步可以并行运行。
- 同一步骤可以同时存在多个活跃批次。
- 一个批次的状态不得阻塞或覆盖其他批次。
- 上下文过长时只提醒和准备交接，不因轮数拒绝继续执行。
- 新 Agent 能依靠小体积状态文件续跑，并避免重复真实写操作。

## 状态模型

`CURRENT_STATE.md` 改为全局并行状态入口，只描述发现、创建、读取和交接规则，不再保存唯一当前批次，也不作为生产互斥锁。

每个批次在自己的运行目录保存独立 `BATCH_STATE.md`。它是该批次唯一权威交接卡，至少记录：

- 状态、步骤、批次 ID 和输入/输出绝对路径；
- 授权范围；
- 已完成且不得重复的真实动作；
- 阻塞、下一条动作和后台进程；
- 可直接复制的接管提示词。

状态使用 `ACTIVE | WAITING_USER | BLOCKED | COMPLETE | ABANDONED`。其他批次处于任何状态都不得阻止新批次运行。防重复判断只针对目标批次，并结合批次目录中的任务清单、日志和 `BATCH_STATE.md`。

新批次创建唯一时间戳目录后立即建立自己的状态文件。续跑时，用户或交接提示词必须提供准确的批次目录或 `BATCH_STATE.md` 路径；表达不明确且找到多个候选批次时，Agent 只询问要接管哪一个，不擅自选择。

## 并发写入

Agent 只修改自己批次的 `BATCH_STATE.md`，不在共享 Markdown 中写实时进度。这样不同步骤和同一步不同批次不会争抢同一个状态文件。`CURRENT_STATE.md` 通过扫描 `runtime/**/BATCH_STATE.md` 发现批次，不维护需要并发更新的中央实时表。

当前 `price_audit_20260808_185049` 交接内容迁移到该批次目录的 `BATCH_STATE.md`，内容和不可重复动作不得丢失。

## 会话生命周期

- 一个任务仍只负责一个步骤、一个批次，但任意数量的其他任务可以并行运行。
- `WAITING_USER` 或 `BLOCKED` 的批次可以在原任务中继续，不强制换任务。
- 批次 `COMPLETE` 或明确 `ABANDONED` 后，原任务才转为历史记录。
- 新步骤或新批次使用新任务；同一批次的接管任务必须读取该批次状态文件。

约 20 轮、三次以上失败重试或大量工具输出时，Agent 提醒一次，并在下一个安全节点更新批次状态，但继续执行。约 30 轮时给出更明确的换任务建议和接管提示词，仍继续当前请求。提醒后每增加约 10 轮才再次提醒，避免反复打断。

上下文轮数本身永远不是暂停或拒绝生产动作的理由。只有真实授权缺失、接口或数据失败、安全红线、无法确认目标批次，或者无法排除重复写操作时才能暂停。

同步修改 `AGENTS.md`、`CURRENT_STATE.md`、`README.md`、三个 runbook 和 `TESTING.md`。文档测试需要验证：

- 明确允许跨步骤及同一步多批次并行；
- `CURRENT_STATE.md` 不再含唯一当前交接卡；
- 每个 runbook 使用批次级 `BATCH_STATE.md`；
- 轮数阈值只提醒、不拒绝执行；
- 当前未完成批次的交接信息已完整迁移。
