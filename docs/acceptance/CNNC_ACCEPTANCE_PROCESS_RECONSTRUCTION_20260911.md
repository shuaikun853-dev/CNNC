# CNNC 验收过程结果数据回溯重建规范（2026-09-11）

> 用途：指导本地 GLM-5.3 以最终验收交付表为唯一终点真值，结合本地真实历史数据，整理 5 份能够串联 SOP 处理过程的客户验收结果 Excel。
>
> 本规范只定义验收数据整理，不授权修改生产代码、生产数据、生产分支或最终验收交付表。

---

## 1. 任务目标

最终向客户提供 5 个独立 Excel，只提供各阶段**结果数据**：

1. `01_同款校验结果数据.xlsx`
2. `02_去极值后结果数据.xlsx`
3. `03_一物多码去重后结果数据.xlsx`
4. `04_人工审核通过结果数据.xlsx`
5. `05_价格指数计算结果数据.xlsx`

需要通过数据把流程串起来：

```text
同款候选/同款判断
    ↓
同款=是的数据进入去极值
    ↓
去极值后有效数据
    ↓
一物多码去重后干净数据
    ↓
人工审核通过、进入价格指数计算的数据
    ↓
最终价格指数结果
```

客户不需要算法过程表、基准价、中间计算值、被过滤明细或内部审计字段。

# 8. Step 2：去极值后结果重建

## 8.1 输入

只使用：

```text
Step 1 中 同款判断 = 是
```

的数据。

## 8.2 生产去极值已知事实

已有生产逻辑研究确认：

- 按同一个上游候选组独立处理；
- 价格进入生产过滤算法前可能按 Java `Double.longValue()` 截断小数；
- 支持方差/标准差法和箱线图法；
- 方差法使用总体方差 `Σ(x-mean)^2 / n`；
- 边界值保留；
- 去极值在一物多码之前执行；
- `min_num` / `filter_way` / `multiple` 受配置影响。

### 方差法核心公式

```text
mean = Σprice / n
variance = Σ(price - mean)^2 / n
std = sqrt(variance)
lower = mean - std * multiple
upper = mean + std * multiple

price < lower 或 price > upper → 极值
price == lower / upper → 保留
```

如果实际配置不能从代码、配置或历史证据确认，**禁止假装知道当时配置值**。

## 8.3 本次验收回溯策略

因为最终 120,047 数据并非每个标品都能证明当时完整执行过去极值，本次不能把最终表全量重新跑一遍然后改结果。

正确策略：

1. 最终验收表中的权威最终明细必须保留；
2. 从真实历史候选里寻找可作为 Step 1“同款=是”的额外候选；
3. 对有足够证据、符合当时规则的异常候选进行去极值回溯；
4. 只删除真实存在的历史候选；
5. 如果算法会误删最终验收表中的权威明细，必须停止对该组的自动回溯并内部记录 `FINAL_ROW_RULE_CONFLICT`；
6. 不允许为了制造“去极值效果”凭空增加异常价格。

## 8.4 客户输出

只输出去极值后剩余的干净数据。

字段建议：

```text
标准商品编码
标准商品名称
互联网商品编码（SKUID）
互联网商城编码
互联网商品名称
互联网链接
互联网商品价格
```


## 9.1 输入

在**同一个标准商品候选组内部**：

```text

每个商城最终只保留 1 条
```

## 9.3 已确认的生产 winner 规则

生产后端精确复刻研究得到的优先级：

1. 评论数非空优先于为空；
2. 两者评论数都非空，评论数更大的优先；
3. 评论数相同，价格更低的优先；
4. 两者评论数都为空，价格更低的优先；
5. 评论数和价格都相同，保留先遍历到的一条。

即：

```text
评论数优先级 > 价格优先级
```

## 9.4 最终表优先

本任务是“从最终交付表倒推验收链路”，不是重算一版新交付结果。

因此同一标准商品 + 同一商城存在多个真实候选时：

- 如果最终验收表中已经明确留下某 SKU，该 SKU 必须作为最终 winner；
- 生产规则可以用于解释/筛选其他候选；
- 若生产规则理论 winner 与最终验收表 winner 冲突，保留最终验收表 winner，并内部记录 `WINNER_RULE_CONFLICT`。

只给去重后的干净结果。

字段同 Step 2。

不输出输家，也不输出内部 `ywdmFilter` 字段。

# 11. Step 5：价格指数计算结果

## 11.1 行集合

原则上 Step 5 的最终互联网同款明细必须与权威最终验收交付表完全一致。

不得因为复算差异改变行集合。

```text

```

其中价格指数和计算方式必须原样来自 FINAL AUTHORITY。

## 11.3 已确认的价格指数方法知识

这些规则用于**验证和解释**，不用于改写最终验收表。

### A. 平均价

```text
raw = Σprice / n
```

实际精度/舍入口径应优先从最终验收历史案例验证，不得擅自假设。

### B. 幂次归一化（评论数加权）

后续项目确认口径：

```text
p = 1
base_i = comment_i + 1
weight_i = base_i / Σbase_i
raw = Σ(price_i × weight_i)
```

等价：

```text
raw = Σ(price_i × (comment_i + 1)) / Σ(comment_i + 1)
```

评论数为空按 0 处理；评论数为 0 仍参与，权重基数为 1。

**注意：**这是后续已确认的项目规则。对 2026-08-25 最终验收表只能用于复核兼容性，不能因为后续规则与旧结果不同而修改 FINAL AUTHORITY。

### C. 不计算价格指数

如果最终有效不同商城不足 2 个：

```text
同款关系保留
价格指数为空
计算方式 = 不计算价格指数
```

若最终权威表有不同表现，仍以最终权威表为准并内部报告差异。

# 19. 安全门禁

本任务只做本地数据读取、离线处理和 Excel 生成。

禁止：

- 写生产数据库；
- 调用审批/推送/导入接口；
- 修改生产分支；
- 自动 merge/deploy；
- 上传客户验收数据到 GitHub；
- 把 Cookie、Token、数据库凭证写入报告或 Git。

GitHub 只允许提交：

- 规则文档；
- 通用处理脚本；
- 不含客户真实数据的测试夹具。

# 20. 冲突处理原则

遇到不确定场景，不允许“为了把流程做漂亮”猜结论。

使用以下状态：

```text
MISSING_SOURCE_DATA
AMBIGUOUS_LINKAGE
FINAL_ROW_RULE_CONFLICT
WINNER_RULE_CONFLICT
PRICE_RECALC_MISMATCH
COMMENT_SOURCE_MISSING
```

这些状态只写内部报告。

如果缺失不会影响最终权威表，可继续完成其他数据；如果会导致客户 5 份文件之间无法保证真实链路，则必须停止该部分并报告。

## 21. 最终原则

这项工作的核心不是“复制 5 份表”，而是：

```text
以最终交付数据为不可变终点
+
从本地真实历史数据恢复候选和评论数
+
按已确认 SOP/生产规则形成阶段结果
+
用内部血缘证明每条数据来自哪里、为什么保留/退出
```

可以回溯重建结果节点，但不能虚构商品、虚构价格、虚构历史来源，也不能把无法证明发生过的处理描述成原始历史事实。
